# v0.3 Automated Transcript Correction

Status: accepted implementation contract; local provider selected, benchmark pending.

Selected local provider: LM Studio through its OpenAI-compatible API, using loopback by
default and an explicit warned opt-in for LAN/VPN/Tailscale-like endpoints. Initial
benchmark candidates are Qwen 2.5 32B Instruct Q4_K_M, Bielik 3.0 11B Q8_0 or F16, and
Qwen 2.5 14B Instruct Q8_0; runtime identifiers are taken exactly from LM Studio.
Ollama remains a later local adapter. OpenRouter with DeepSeek V3 and Qwen 2.5 72B
Instruct follows only after local baselines and separate cloud authorization.

## 1. Scope

v0.3 adds conservative automated correction to the existing immutable revision system.
It also delivers the separately scoped fresh-install verification script and README
onboarding work recorded in the roadmap. Translation, HTML export, project dictionaries,
and advanced 3+ channel handling are not part of v0.3.

Automated correction is not prose editing. Its output must remain a faithful record of
what was spoken, including malformed sentences, fillers, repetitions, self-corrections,
and stylistic quirks.

## 2. Architectural boundary

The dependency direction is:

```text
CLI / future GUI
        |
        v
correction application service
        |
        +--> consent policy
        +--> deterministic chunk planner
        +--> provider protocol --> mock/local/cloud adapter
        +--> response validator
        |
        v
existing review alignment + RevisionEngine + revision storage
```

Providers return suggestions; they never construct `TranscriptRevision`, allocate a
revision number, write artifacts, or decide authoritative word mappings. Provider SDKs
and HTTP clients stay in adapters and are not imported by the revision domain.

## 3. Selected source

One run selects exactly one immutable source:

- raw completed canonical result; or
- one compatible full-snapshot revision.

The selected source resolves to `EffectiveTranscript`. A generated LLM revision is a
complete standalone revision snapshot tied to the canonical base and may identify the
selected revision as its parent. Canonical data remains unchanged.

## 4. Deterministic chunks

Chunk planning operates on ordered effective tokens, never arbitrary character slices.
Every token belongs to exactly one editable range. Adjacent read-only context may be
included in requests but is marked non-editable and cannot appear in accepted corrected
output.

Configuration exposes:

```toml
[correction]
target_tokens = 600
max_tokens = 800
context_tokens = 80
```

These are initial application-token defaults, not provider tokenizer limits. The planner
prefers nearby speaker, sentence, and canonical-anchor boundaries, but `max_tokens` is a
hard editable-range limit. It records stable zero-based source ranges and a content hash
for resume verification.

## 5. Provider-neutral request and response

A request contains:

- schema/prompt version and operation ID;
- language;
- ordered editable tokens with stable local/source identities and speakers;
- separately marked preceding/following read-only context;
- correction policy and allowed change categories.

A valid provider response contains corrected editable text in the same ordered speaker
blocks supplied by the application. Block count/order/identity are immutable. The local
application diffs each block against its owned source tokens and derives exact source spans,
before/after text, and one deterministic category:

- `asr_lexical`;
- `proper_name`;
- `punctuation`;
- `capitalization`;
- `sentence_boundary`.

Unknown response fields, malformed corrected text, ambiguous speaker-boundary insertions,
or a response that includes read-only context are rejected. The local aligner reconstructs
the authoritative mapping and audit independently. Optional future provider annotations
are retained only as advisory benchmark evidence.

## 6. Privacy and consent

Endpoint kinds are `local` and `cloud`. Both are external API boundaries and require the
warnings defined in `11-security-and-privacy.md`. Consent is evaluated before request
serialization or provider invocation.

Interactive choices are reject, accept once, and persistently accept for the exact
provider, non-secret endpoint identity, operation class, and warning-policy version.
Non-interactive execution requires an explicit one-run acceptance or matching stored
consent. Strict offline mode rejects cloud endpoints. Credentials are read only from
provider-specific environment variables or a future secure store and are never persisted.

The deterministic mock provider is in-process test infrastructure, performs no API call,
and requires no privacy consent.

## 7. Failure, retry, resume, and batches

Each editable chunk has an immutable operation identity derived from selected-source,
prompt, correction configuration, and chunk hashes. Completed validated responses may be
resumed only when all identity inputs still match.

Retries are bounded and apply only to explicitly retryable transport/rate-limit/server
failures. Invalid provider content is permanent for that attempt and is never silently
accepted. A partial job publishes no transcript revision. Directory processing is
deterministically ordered, non-recursive by default, and isolates job failures according
to the existing batch continuation setting.

## 8. Provenance and artifacts

Published revisions use `provenance.method = "llm"` and record provider, model,
`local|cloud`, prompt ID/hash, and non-secret effective parameters. Detailed audits add
the independently reconstructed local change list. Optional provider annotations, when a
provider supports them, remain separate evidence and never become the patch. Secrets and
full request payloads are excluded.

## 9. Benchmark contract

Private benchmark data stays outside Git. A non-secret manifest selects inputs and gold
by exact hashes and revision lineage. Supported comparisons are:

- canonical result to latest accepted gold;
- earlier compatible revision to latest accepted gold.

The repository contains only synthetic fixtures and generic tooling. Reports include the
metrics required by FR-K18 and enough non-secret configuration/provenance to reproduce a
run. Provider benchmarks are reported separately; a cloud score must not be presented as
a local-provider score or vice versa.

Initial adapter smoke evidence: Qwen 2.5 14B Instruct Q8_0 accepted the synthetic example
under `faithful-correction-v3` with 8 revision tokens and no warnings. Earlier responses
were deliberately rejected for an exact-text mismatch and for a contradictory change
record; those failures drove the stricter prompt and category validation. Resume reuse and
immutable publication then passed without a second LM Studio request. The canonical input
remained unchanged, the revision was published separately, and resume/revision/lock files
were all mode `0600`. This completes the synthetic adapter smoke gate.

The first private-corpus pilot exposed unreliable numeric span counting: Qwen copied the
exact source token from editable position 65 but labelled it as position 59. Prompt v4 and
the LM Studio wire schema therefore address change spans with copied inclusive stable token
IDs. The adapter deterministically converts those IDs to the provider-neutral half-open
indexes, rejects context/unknown/reversed IDs, and retains exact before/after and full-text
reconstruction checks. This is a universal protocol correction, not a corpus-specific rule.

The next shortest-case rerun showed that `end_token_id` was interpreted as exclusive even
when declared inclusive. Prompt v5 removes start/end boundary semantics: every proposed
change lists all affected stable token IDs in order. The adapter requires a non-empty,
unique, ordered, contiguous editable list and derives the core half-open span locally.

The first v5 response grouped non-adjacent token IDs into one change. Prompt v6 defines
each change object as one contiguous source replacement, requires the complete contiguous
span for multi-token replacements, and requires separate objects for non-adjacent edits.

The next response addressed the correct two-token span but removed source punctuation from
its `before` audit copy. Prompt v7 requires the smallest sufficient span, makes `before`
explicitly copy-only, and includes a generic capitalization example that keeps punctuation
and excludes an unchanged following token. Exact local source matching remains mandatory.

The v7 response then copied an exact 11-token `before` span but supplied only four token
IDs. Prompt v8 removes end and span-list generation: the provider supplies one stable start
token ID plus exact `before` text, and the adapter derives the unique contiguous end locally.
Unknown/context starts and zero/ambiguous exact matches remain hard failures.

The v8 small-chunk rerun still selected the wrong start token. The accepted redesign now
mirrors the human-review boundary: prompt v9 asks only for corrected editable transcript
text, while the local application deterministically derives insertions, deletions,
replacements, categories, speaker mapping, alignment, and audit. This preserves FR-K03 and
removes unreliable redundant patch metadata from the model's responsibilities.

The first v9 response produced locally derived edits that crossed a speaker boundary
because plain corrected text no longer carried the boundary. Prompt v10 mirrors human
review more closely: the request and response contain the same ordered speaker blocks.
Block count, order, and IDs are immutable, and local diff/alignment runs independently
inside each block, making cross-speaker edits structurally impossible.

The three-case Qwen 2.5 14B Q8_0 v10 pilot completed technically but failed the quality
gate. Under annotation-excluding correction normalization, raw canonical text had
`0.00747664` WER against manual gold while the LLM candidate had `0.01151008`; the model
output was therefore about 54% farther from gold. Manual review also found paraphrasing,
stylistic edits, introduced grammar errors, missed ASR errors, and inconsistent proper
names. Prompt v11 makes copying the default, permits only minimal high-confidence ASR or
proper-name replacements, forbids grammar-repair insertions/deletions and optional project
terminology normalization without a dictionary, and requires no change where alternatives
or intent are uncertain. v10 remains preserved as a rejected pilot, not a full-corpus run.

The v11 rerun also failed the three-case gate. It reached `0.02056075` WER against gold,
versus `0.00747664` for raw ASR and `0.01151008` for v10. One short case lost 102 of 855
source tokens and produced one downstream speaker reassignment despite immutable provider
block IDs. Prompt compliance is therefore not a safety boundary. The adapter now rejects
any speaker block whose token-count drift exceeds the larger of four tokens or 10%, and
the revision boundary rejects every automated result with a nonzero speaker-change count.
These corpus-independent gates execute before publication and remain mandatory for later
prompts and providers. v11 is preserved as a rejected pilot, not run on the full corpus.

The Bielik 3.0 11B Q8_0 pilot on LM Studio 0.4.21 exposed an engine-level compatibility
failure: ordinary chat generation succeeded, while even a minimal JSON-schema request
failed when an `assistant` chat-template token reached llama.cpp's grammar sampler. The
LM Studio adapter therefore retains grammar-constrained `json-schema` as its default and
adds an explicit `json-text` compatibility mode. This mode omits only `response_format`;
strict whole-response JSON/schema validation and every local correction safety gate remain
mandatory. It is recorded through mode-specific prompt identity and must be benchmarked
separately rather than silently selected after a provider error.

After enabling the explicit plain-JSON mode, the same Bielik build passed the short,
medium, and long contract previews and published all three revisions from private cached
responses. It changed only five tokens across 10,151 source tokens: three substitutions
and two deletions, with no insertions or speaker changes. One medium-case alignment was
ambiguous but non-fatal. Under `ewp-correction-lexical-v2`, raw canonical text scored
`0.00747664` WER against manual gold, while Bielik scored `0.00767339`; the candidate was
therefore about 2.6% farther from gold than raw ASR. Canonical-to-Bielik WER was only
`0.00049179`, confirming substantially more conservative behavior than either Qwen pilot.
The run passes adapter safety but does not pass the quality gate; its three substitutions
and deletion span require manual classification before deciding whether prompt changes are
justified. This evidence is configuration-specific to Bielik 3.0 11B Instruct Q8_0,
32K context, temperature zero, and LM Studio 0.4.21 using the `json-text` fallback.

## 10. Acceptance checklist

### Contract and deterministic core

- [x] All FR-K and NFR-015/016 requirements are traced with explicit implementation
  status in `20-mvp-requirements-traceability.md`.
- [ ] Short/long, multi-speaker, punctuation, repeated-word, and boundary fixtures prove
  gap-free single ownership with read-only overlap.
- [ ] A deterministic mock provider completes raw-to-revision and revision-to-child
  correction without network access or model loading.
- [x] Provider identity/schema failures and locally derived change/reconstruction failures
  stop before revision publication; read-only context is structurally separate and
  explicitly excluded by the provider output contract.

### Privacy and operations

- [ ] Reject, accept-once, persistent scoped consent, changed-scope reprompt, strict
  offline cloud rejection, and non-interactive behavior have zero-secret automated tests.
- [x] Timeout budgets, retryable/permanent failure classification, invalid response,
  resume, stale-resume rejection, and
  mixed-success batch behavior are covered.
- [ ] Logs, errors, revisions, audits, reports, and configuration artifacts pass secret
  and unintended transcript-payload scans.

### Benchmarks and providers

  non-lexical and aggregate operational metrics are still pending.
- [ ] The private corpus produces a manifest audit and baseline mock report without
  entering Git.
- [ ] One user-selected local API provider and one user-selected cloud provider pass
  contract tests and representative manual review.
- [ ] Any paid/network benchmark runs require separate user authorization.

### Distribution
