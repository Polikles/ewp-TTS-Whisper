# v0.3 Automated Transcript Correction

Status: accepted implementation contract; local baseline complete, cloud adapter ready for
an explicitly authorized paid pilot.

Selected local provider: LM Studio through its OpenAI-compatible API, using loopback by
default and an explicit warned opt-in for LAN/VPN/Tailscale-like endpoints. Initial
benchmark candidates are Qwen 2.5 32B Instruct Q4_K_M, Bielik 3.0 11B Q8_0 or F16, and
Qwen 2.5 14B Instruct Q8_0; runtime identifiers are taken exactly from LM Studio.
Ollama remains a later local adapter. OpenRouter is implemented for the separately
authorized cloud pilot; exact live model slugs must be checked immediately before a paid
run because the provider catalog can change.

## 1. Scope

v0.3 adds conservative automated correction to the existing immutable revision system.
It also delivers the separately scoped fresh-install verification script and README
onboarding work recorded in the roadmap. Translation, HTML export, project dictionaries,
and advanced 3+ channel handling are not part of v0.3.

Automated correction is not prose editing. Its output must remain a faithful record of
what was spoken, including malformed sentences, fillers, repetitions, self-corrections,
and stylistic quirks.

An LLM revision is always a non-final review candidate. Passing schema validation, lexical
WER/CER, or an automated quality threshold cannot establish correct punctuation, quotation
marks, speaker attribution, sentence boundaries, or complete faithfulness. A human must
accept those dimensions before the revision is used as publication text or benchmark gold.

## 2. Architectural boundary

The dependency direction is:

```text
CLI / future GUI
        |
        v
correction application service
        |
        +--> consent policy
        +--> deterministic chunk planner
        +--> provider protocol --> mock/local/cloud adapter
        +--> response validator
        |
        v
existing review alignment + RevisionEngine + revision storage
```

Providers return suggestions; they never construct `TranscriptRevision`, allocate a
revision number, write artifacts, or decide authoritative word mappings. Provider SDKs
and HTTP clients stay in adapters and are not imported by the revision domain.

## 3. Selected source

One run selects exactly one immutable source:

- raw completed canonical result; or
- one compatible full-snapshot revision.

The selected source resolves to `EffectiveTranscript`. A generated LLM revision is a
complete standalone revision snapshot tied to the canonical base and may identify the
selected revision as its parent. Canonical data remains unchanged.

## 4. Deterministic chunks

Chunk planning operates on ordered effective tokens, never arbitrary character slices.
Every token belongs to exactly one editable range. Adjacent read-only context may be
included in requests but is marked non-editable and cannot appear in accepted corrected
output.

Configuration exposes:

```toml
[correction]
target_tokens = 600
max_tokens = 800
context_tokens = 80
```

These are initial application-token defaults, not provider tokenizer limits. The planner
prefers nearby speaker, sentence, and canonical-anchor boundaries, but `max_tokens` is a
hard editable-range limit. It records stable zero-based source ranges and a content hash
for resume verification.

## 5. Provider-neutral request and response

A request contains:

- schema/prompt version and operation ID;
- language;
- ordered editable tokens with stable local/source identities and speakers;
- separately marked preceding/following read-only context;
- correction policy and allowed change categories.

The operation ID is local request/resume identity. A structured provider response may
echo it for diagnostics, but the synchronous response is bound to the active request
locally and the echoed copy is not trusted as an acceptance condition. Resume state still
requires the exact locally computed operation identity. This avoids treating model copying
of an opaque hash as a security boundary.

A valid provider response contains corrected editable text in the same ordered speaker
blocks supplied by the application. Block count/order/identity are immutable. The local
application diffs each block against its owned source tokens and derives exact source spans,
before/after text, and one deterministic category:

- `asr_lexical`;
- `proper_name`;
- `punctuation`;
- `capitalization`;
- `sentence_boundary`.

Unknown response fields, malformed corrected text, ambiguous speaker-boundary insertions,
or a response that includes read-only context are rejected. The local aligner reconstructs
the authoritative mapping and audit independently. Optional future provider annotations
are retained only as advisory benchmark evidence.
For automated correction, canonical speaker boundaries are also hard constraints during
local alignment. This prevents repeated or ambiguous words from being mapped to an adjacent
speaker even though the provider returned the correct immutable block identities. Manual
review continues to permit explicit speaker reassignment.

## 6. Privacy and consent

Endpoint kinds are `local` and `cloud`. Both are external API boundaries and require the
warnings defined in `11-security-and-privacy.md`. Consent is evaluated before request
serialization or provider invocation.

Interactive choices are reject, accept once, and persistently accept for the exact
provider, non-secret endpoint identity, operation class, and warning-policy version.
Non-interactive execution requires an explicit one-run acceptance or matching stored
consent. Strict offline mode rejects cloud endpoints. Credentials are read only from
provider-specific environment variables or a future secure store and are never persisted.

The OpenRouter adapter reads `OPENROUTER_API_KEY` lazily after consent, requires HTTPS,
disables provider fallback, requires support for requested structured parameters, captures
provider-reported tokens/cost, and never stores the bearer secret. Strict offline remains
the default; `--allow-cloud` changes it only for the explicit command. Implementation and
network-isolated tests do not authorize a paid request.
Reasoning-capable cloud models expose an optional explicit token budget. The budget is
included in request identity and provenance; disabled/default/enabled reasoning are
different benchmark configurations and must not be merged in one comparison row.

The deterministic mock provider is in-process test infrastructure, performs no API call,
and requires no privacy consent.

## 7. Failure, retry, resume, and batches

Each editable chunk has an immutable operation identity derived from selected-source,
prompt, correction configuration, and chunk hashes. Completed validated responses may be
resumed only when all identity inputs still match.

Retries are bounded and apply only to explicitly retryable transport/rate-limit/server
failures. Invalid provider content is permanent for that attempt and is never silently
accepted. A partial job publishes no transcript revision. Directory processing is
deterministically ordered, non-recursive by default, and isolates job failures according
to the existing batch continuation setting.

## 8. Provenance and artifacts

Published revisions use `provenance.method = "llm"` and record provider, model,
`local|cloud`, prompt ID/hash, and non-secret effective parameters. Detailed audits add
the independently reconstructed local change list. Optional provider annotations, when a
provider supports them, remain separate evidence and never become the patch. Secrets and
full request payloads are excluded.

## 9. Benchmark contract

Private benchmark data stays outside Git. A non-secret manifest selects inputs and gold
by exact hashes and revision lineage. Supported comparisons are:

- canonical result to latest accepted gold;
- earlier compatible revision to latest accepted gold.

The repository contains only synthetic fixtures and generic tooling. Reports include the
metrics required by FR-K18 and enough non-secret configuration/provenance to reproduce a
run. Provider benchmarks are reported separately; a cloud score must not be presented as
a local-provider score or vice versa.

Initial adapter smoke evidence: Qwen 2.5 14B Instruct Q8_0 accepted the synthetic example
under `faithful-correction-v3` with 8 revision tokens and no warnings. Earlier responses
were deliberately rejected for an exact-text mismatch and for a contradictory change
record; those failures drove the stricter prompt and category validation. Resume reuse and
immutable publication then passed without a second LM Studio request. The canonical input
remained unchanged, the revision was published separately, and resume/revision/lock files
were all mode `0600`. This completes the synthetic adapter smoke gate.

The first private-corpus pilot exposed unreliable numeric span counting: Qwen copied the
exact source token from editable position 65 but labelled it as position 59. Prompt v4 and
the LM Studio wire schema therefore address change spans with copied inclusive stable token
IDs. The adapter deterministically converts those IDs to the provider-neutral half-open
indexes, rejects context/unknown/reversed IDs, and retains exact before/after and full-text
reconstruction checks. This is a universal protocol correction, not a corpus-specific rule.

The next shortest-case rerun showed that `end_token_id` was interpreted as exclusive even
when declared inclusive. Prompt v5 removes start/end boundary semantics: every proposed
change lists all affected stable token IDs in order. The adapter requires a non-empty,
unique, ordered, contiguous editable list and derives the core half-open span locally.

The first v5 response grouped non-adjacent token IDs into one change. Prompt v6 defines
each change object as one contiguous source replacement, requires the complete contiguous
span for multi-token replacements, and requires separate objects for non-adjacent edits.

The next response addressed the correct two-token span but removed source punctuation from
its `before` audit copy. Prompt v7 requires the smallest sufficient span, makes `before`
explicitly copy-only, and includes a generic capitalization example that keeps punctuation
and excludes an unchanged following token. Exact local source matching remains mandatory.

The v7 response then copied an exact 11-token `before` span but supplied only four token
IDs. Prompt v8 removes end and span-list generation: the provider supplies one stable start
token ID plus exact `before` text, and the adapter derives the unique contiguous end locally.
Unknown/context starts and zero/ambiguous exact matches remain hard failures.

The v8 small-chunk rerun still selected the wrong start token. The accepted redesign now
mirrors the human-review boundary: prompt v9 asks only for corrected editable transcript
text, while the local application deterministically derives insertions, deletions,
replacements, categories, speaker mapping, alignment, and audit. This preserves FR-K03 and
removes unreliable redundant patch metadata from the model's responsibilities.

The first v9 response produced locally derived edits that crossed a speaker boundary
because plain corrected text no longer carried the boundary. Prompt v10 mirrors human
review more closely: the request and response contain the same ordered speaker blocks.
Block count, order, and IDs are immutable, and local diff/alignment runs independently
inside each block, making cross-speaker edits structurally impossible.

The three-case Qwen 2.5 14B Q8_0 v10 pilot completed technically but failed the quality
gate. Under annotation-excluding correction normalization, raw canonical text had
`0.00747664` WER against manual gold while the LLM candidate had `0.01151008`; the model
output was therefore about 54% farther from gold. Manual review also found paraphrasing,
stylistic edits, introduced grammar errors, missed ASR errors, and inconsistent proper
names. Prompt v11 makes copying the default, permits only minimal high-confidence ASR or
proper-name replacements, forbids grammar-repair insertions/deletions and optional project
terminology normalization without a dictionary, and requires no change where alternatives
or intent are uncertain. v10 remains preserved as a rejected pilot, not a full-corpus run.

The v11 rerun also failed the three-case gate. It reached `0.02056075` WER against gold,
versus `0.00747664` for raw ASR and `0.01151008` for v10. One short case lost 102 of 855
source tokens and produced one downstream speaker reassignment despite immutable provider
block IDs. Prompt compliance is therefore not a safety boundary. The adapter now rejects
any speaker block whose token-count drift exceeds the larger of four tokens or 10%, and
the revision boundary rejects every automated result with a nonzero speaker-change count.
It also requires the ordered sequence of recognized digit-based numeric literals to remain
exactly unchanged, so a model cannot publish changes such as `5.2` to `4.0`; punctuation
around an unchanged number remains editable. These corpus-independent gates execute before
publication and remain mandatory for later prompts and providers. v11 is preserved as a
rejected pilot, not run on the full corpus.

The Bielik 3.0 11B Q8_0 pilot on LM Studio 0.4.21 exposed an engine-level compatibility
failure: ordinary chat generation succeeded, while even a minimal JSON-schema request
failed when an `assistant` chat-template token reached llama.cpp's grammar sampler. The
LM Studio adapter therefore retains grammar-constrained `json-schema` as its default and
adds an explicit `json-text` compatibility mode. This mode omits only `response_format`;
strict whole-response JSON/schema validation and every local correction safety gate remain
mandatory. It is recorded through mode-specific prompt identity and must be benchmarked
separately rather than silently selected after a provider error.

After enabling the explicit plain-JSON mode, the same Bielik build passed the short,
medium, and long contract previews and published all three revisions from private cached
responses. It changed only five tokens across 10,151 source tokens: three substitutions
and two deletions, with no insertions or speaker changes. One medium-case alignment was
ambiguous but non-fatal. Under `ewp-correction-lexical-v2`, raw canonical text scored
`0.00747664` WER against manual gold, while Bielik scored `0.00767339`; the candidate was
therefore about 2.6% farther from gold than raw ASR. Canonical-to-Bielik WER was only
`0.00049179`, confirming substantially more conservative behavior than either Qwen pilot.
The run passes adapter safety but does not pass the quality gate; its three substitutions
and deletion span were manually classified. `postrzymać` to `powstrzymać` was the sole
correct repair. `wparcie` to `wsparcie` remained wrong against the accepted `parcie`;
`zadaniu` to `są` introduced a substitution error; and deleting `dwa razy,` removed two
spoken words. The valid repair removed one word error while the substitution and deletion
introduced three, exactly explaining the net two-error regression. Bielik therefore made
one useful correction among five affected tokens and is not a substitute for manual review
under this prompt. This evidence is configuration-specific to Bielik 3.0 11B Instruct Q8_0,
32K context, temperature zero, and LM Studio 0.4.21 using the `json-text` fallback.

The controlled Bielik 11B F16 rerun used prompt v11, the compact speaker-block contract,
120/160/30 chunks, 8K context, temperature zero, and `json-text`. It consumed about
21.7 GB VRAM and completed the three previews in 285.92, 712.16, and 2,390.47 seconds:
3,388.55 seconds total (56 minutes 29 seconds). Its aggregate metrics exactly matched the
earlier Q8 result: `0.00049179` WER from raw and `0.00767339` against gold, still 2.6%
worse than raw ASR.

Manual audit found the same substantive Q8 behavior: one correct `postrzymać.` to
`powstrzymać.` repair; the still-wrong `wparcie` to `wsparcie` guess; deletion of spoken
`dwa razy,`; and harmful `zadaniu` to `są`. F16 added only `damian.` to `Damian.` in two
cases and `Czym` to `czym` capitalization changes, which lexical normalization does not
score. F16 therefore provides no demonstrated quality advantage over Q8 while imposing
substantially higher runtime, and is rejected for this configuration.

The fair current-contract Bielik Q8 control used the identical prompt v11, compact
speaker-block request, `json-text`, 120/160/30 chunks, 8K context, temperature zero, and
sampling defaults. At approximately 20.9 GB VRAM it completed the three cases in 61.59,
153.72, and 519.39 seconds: 734.70 seconds total (12 minutes 15 seconds). It scored
`0.00039343` WER from raw and `0.00757501` against gold, about 1.3% worse than raw ASR but
better than F16. Audit found seven changes: two `damian.` capitalization repairs, one
`Czym` case change, one correct `postrzymać.` to `powstrzymać.` repair, the still-wrong
`wparcie` to `wsparcie` guess, and deletion of spoken `dwa razy,`; S2E9 was unchanged.
The correct lexical repair removed one error and the deletion added two, exactly explaining
the net one-error regression. Q8 is preferred over F16 for efficiency, but Bielik still
fails the correction-quality gate and does not justify a full-corpus run.

No local candidate passes as a final automatic correction stage. Qwen 32B small chunks is

plain-JSON response-contract violations, an opaque-ID copy mutation, context exhaustion
from obsolete request metadata, a transient zero-log connection failure, alignment
ambiguity, destructive-output rejection, and unmeasured human review time. Future reports
must identify prompt content hash as well as prompt label so prompt revisions are compared
rather than conflated.

### Cloud three-case comparison

The separately authorized OpenRouter pilot used prompt v11, the compact speaker-block
contract, 120/160/30 chunks, temperature zero, disabled provider fallback, and exact model
slugs. Paid previews were retained only in private mode-0600 resume state; publication and
audit reused those responses without another model request.

| Candidate | Reasoning | WER vs gold | Errors | Runtime | Cost | Manual outcome |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| Raw ASR | n/a | `0.00747664` | 76 | n/a | n/a | Required baseline |
| DeepSeek V3 0324 | provider default | `0.00659124` | 67 | 19m31s | `$0.088462` | Net improvement; deletions/context edits require review |
| Gemini 2.5 Flash | disabled (`0`) | `0.00619774` | 63 | 3m01s | `$0.155583` | Leading pilot; reviewed edits accepted in gold context |

DeepSeek removed nine baseline errors, an 11.8% reduction. Gemini removed 13, a 17.1%
reduction, and was about 6.5 times faster in preview wall time, although its reported cost
was higher. Human review accepted Gemini's context-dependent inflection and proper-name
changes after comparison with gold; they must not be generalized as globally safe
substitutions. Gemini remains a review-candidate generator: lexical scoring still leaves
63 disagreements and cannot validate quotation marks, punctuation, speakers, or complete
spoken-form faithfulness.

A preliminary Qwen 2.5 72B OpenRouter short case used the larger 600/800/80 defaults and
cost `$0.004423`; it deleted a spoken token and failed manual review, so no longer paid run
was performed. It is not directly comparable to the formal rows and remains rejected pilot
evidence. Total recorded cloud spend stayed well below the separately authorized cap.

A Gemini 2.5 Flash short-case control with an explicit 1,024-token reasoning budget made
the same three lexical repairs as the disabled-reasoning baseline and omitted only the
unscored `Czym` to `czym` capitalization edit. It took 36.03 rather than 15.40 seconds and
cost `$0.023812` rather than `$0.012960`: 2.34 times slower and 1.84 times more expensive
without a lexical-quality gain. The reasoning branch was therefore stopped before longer
paid cases; reasoning-disabled Gemini remains the comparable baseline.

### Gemini full-corpus baseline

The reasoning-disabled Gemini 2.5 Flash profile subsequently completed all 24 private
benchmark episodes (77,607 raw transcript words) with prompt v11 and 120/160/30 chunking.
All 24 candidate revisions and all 24 content-free audits were produced. The exact-lineage
report measured raw ASR at `0.01077914` WER against manual gold and the Gemini candidate at
`0.00889891`, a 17.44% relative lexical-error reduction. Canonical-to-candidate WER was
`0.00338242`. Report v3 counted 146 net lexical errors removed: 21 episodes improved, 2
were unchanged, and 1 regressed. This is the first complete cloud correction baseline,
not acceptance as a final transcript: every candidate still requires human review, and
the regressed episode is the first targeted audit case.

Targeted review of the nominally regressed `S2E1` case found that manual gold was itself
imperfect. Gemini correctly changed `postanowiamy` to `postanawiamy` and `króciczkami` to
`króliczkami`; those repairs were scored as errors because both mistakes survived manual
review. Conversely, changing spoken `5.2` to `4.0` introduced a real factual error. The
reported aggregate therefore remains reproducible for the hashed gold revision but is
provisional as a quality estimate until corrected gold is published as a later immutable
revision and the report is regenerated. This is direct evidence that manual gold requires
versioning and validation rather than being treated as infallible.

The audits contain 395 operations: 190 substitutions, 140 punctuation-only changes, 26
deletions, 22 splits, 11 insertions, and 6 merges. Nineteen deterministic alignment
warnings were retained, while speaker changes remained zero. These counts describe model
activity and alignment, not correctness; edit precision, stylistic faithfulness,
quotation marks, punctuation, and speaker attribution still require comparison with the
recording and manual gold.

Operator wall time, including observed failed attempts and retries, was about 25 minutes
21 seconds. Validated private resume records account for 651 accepted requests, 2,136,251
input tokens, 231,079 output tokens, and `$1.218604`. The OpenRouter billing screen showed
about `$1.34`; the difference is expected because rejected or malformed provider responses
are billed externally but are deliberately absent from validated resume state. Provider
billing remains authoritative. The run stayed well below the separately authorized cap.

The full run also supplied recovery evidence rather than only quality evidence. One
speaker-alignment rejection was corrected by constraining automated alignment to preserve
speaker ownership; one echoed operation-ID mismatch was removed by binding synchronous
responses locally; and intermittent invalid/truncated JSON responses succeeded through
bounded retry or cached rerun. No private transcript, response, revision, or audit artifact
is committed to this repository.

Correction benchmark report v3 now exposes the net lexical word-error reduction, relative
reduction, source-to-candidate word edit distance, net correction efficiency, and counts
of improved, unchanged, and regressed cases. These are content-free operational metrics,
not edit precision: a positive net result can still contain harmful individual changes.

The first Qwen 2.5 32B text-only pilot at an 8K context exposed obsolete wire overhead:
one 120-token editable chunk consumed 8,058 prompt tokens and its JSON response was cut off
after 134 completion tokens at exactly 8,192 total. Since the v10 speaker-block contract no
longer asks the provider to address individual token metadata, the adapter now sends only
read-only context and editable speaker-block text. Exact token IDs remain local inputs to
deterministic diff, mapping, reconstruction, and revision validation. A versioned request
contract participates in the prompt hash so pre-change resume responses cannot be reused.

With the compact contract, Qwen 2.5 32B Instruct completed the same three-case pilot in
JSON-schema mode at 8K context, temperature zero, and approximately 23 GB VRAM. All 10,151
revision tokens published with zero warnings or speaker changes. Runtime was 2,200.66
seconds (about 36 minutes 41 seconds), or approximately 4.6 transcript tokens per second
with 120/160/30 chunk settings. Its WER against manual gold was `0.00737826`, a 1.3%
improvement over raw ASR at `0.00747664`; canonical-to-candidate WER was `0.00059014`.

Manual audit prevents treating that small aggregate gain as an unconditional pass. Five
changes were clearly useful: two recurring `damian.` to `Damian.` capitalization repairs,
`ogarnię` to `ogarnie`, `odwiercielenie` to `odzwierciedlenie`, and restoration of the
spoken email address. Two were harmful: `kazusie` to the stylistic synonym `przypadku`
violated faithfulness, while `reddicie.` to `reddite.` introduced an incorrect proper-name
form. Two punctuation-only edits require transcript-context review and do not affect the
lexical score; manual review accepted both as valid alternative punctuation. The
one-net-word improvement is therefore genuine but too small to justify
a full-corpus run at the measured speed. A larger-chunk pilot must next test throughput and
whether harmful-edit behavior remains bounded.

The Qwen 32B 400/500/60 preview rerun completed all three cases without warnings at the
same prompt/model/output-mode settings. It took 162.58, 420.46, and 1,416.44 seconds,
respectively: 1,999.48 seconds total (33 minutes 19 seconds), only about 9.1% faster than
the 120/160/30 baseline. The medium candidate contained 2,078 tokens rather than 2,079, so
publication, lexical scoring, and manual audit remain mandatory before this chunk profile
can be accepted or rejected.

Publication and audit rejected the 400/500/60 profile. Its WER against gold was
`0.00747664`, identical to raw ASR and worse than the 120/160/30 candidate at `0.00737826`.
It made 11 audited changes rather than nine. Useful recurring repairs included `damian.`
to `Damian.`, `ogarnię` to `ogarnie`, and `odwiercielenie` to `odzwierciedlenie`, but it
also deleted `umieć`, repeated the incorrect `reddicie.` to `reddite.` change, and changed
grammatical forms such as `zdobyć` to `zdobywać` and `informacje` to `informacji` without
evidence that stylistic/grammar repair was appropriate. Remaining case/punctuation changes
do not rescue the profile: a 9.1% runtime reduction does not offset more reviewer work,
deletion risk, and loss of the small lexical gain. The 120/160/30 run remains the Qwen 32B
pilot baseline; neither profile currently justifies a full-corpus run.
