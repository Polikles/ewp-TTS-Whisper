# v0.3 Automated Transcript Correction

Status: accepted implementation contract; local provider selected, benchmark pending.

Selected local provider: LM Studio through its OpenAI-compatible API, using loopback by
default and an explicit warned opt-in for LAN/VPN/Tailscale-like endpoints. Initial
benchmark candidates are Qwen 2.5 32B Instruct Q4_K_M, Bielik 3.0 11B Q8_0 or F16, and
Qwen 2.5 14B Instruct Q8_0; runtime identifiers are taken exactly from LM Studio.
Ollama remains a later local adapter. OpenRouter with DeepSeek V3 and Qwen 2.5 72B
Instruct follows only after local baselines and separate cloud authorization.

## 1. Scope

v0.3 adds conservative automated correction to the existing immutable revision system.
It also delivers the separately scoped fresh-install verification script and README
onboarding work recorded in the roadmap. Translation, HTML export, project dictionaries,
and advanced 3+ channel handling are not part of v0.3.

Automated correction is not prose editing. Its output must remain a faithful record of
what was spoken, including malformed sentences, fillers, repetitions, self-corrections,
and stylistic quirks.

## 2. Architectural boundary

The dependency direction is:

```text
CLI / future GUI
        |
        v
correction application service
        |
        +--> consent policy
        +--> deterministic chunk planner
        +--> provider protocol --> mock/local/cloud adapter
        +--> response validator
        |
        v
existing review alignment + RevisionEngine + revision storage
```

Providers return suggestions; they never construct `TranscriptRevision`, allocate a
revision number, write artifacts, or decide authoritative word mappings. Provider SDKs
and HTTP clients stay in adapters and are not imported by the revision domain.

## 3. Selected source

One run selects exactly one immutable source:

- raw completed canonical result; or
- one compatible full-snapshot revision.

The selected source resolves to `EffectiveTranscript`. A generated LLM revision is a
complete standalone revision snapshot tied to the canonical base and may identify the
selected revision as its parent. Canonical data remains unchanged.

## 4. Deterministic chunks

Chunk planning operates on ordered effective tokens, never arbitrary character slices.
Every token belongs to exactly one editable range. Adjacent read-only context may be
included in requests but is marked non-editable and cannot appear in accepted corrected
output.

Configuration exposes:

```toml
[correction]
target_tokens = 600
max_tokens = 800
context_tokens = 80
```

These are initial application-token defaults, not provider tokenizer limits. The planner
prefers nearby speaker, sentence, and canonical-anchor boundaries, but `max_tokens` is a
hard editable-range limit. It records stable zero-based source ranges and a content hash
for resume verification.

## 5. Provider-neutral request and response

A request contains:

- schema/prompt version and operation ID;
- language;
- ordered editable tokens with stable local/source identities and speakers;
- separately marked preceding/following read-only context;
- correction policy and allowed change categories.

A valid response contains corrected editable text and proposed changes. Every proposed
change contains a source span, exact before text, exact after text, and one category:

- `asr_lexical`;
- `proper_name`;
- `punctuation`;
- `capitalization`;
- `sentence_boundary`.

Unknown fields/categories, malformed spans, changes outside the editable range, or a
response that rewrites read-only context are rejected. The local aligner reconstructs
the authoritative mapping and audit independently.

## 6. Privacy and consent

Endpoint kinds are `local` and `cloud`. Both are external API boundaries and require the
warnings defined in `11-security-and-privacy.md`. Consent is evaluated before request
serialization or provider invocation.

Interactive choices are reject, accept once, and persistently accept for the exact
provider, non-secret endpoint identity, operation class, and warning-policy version.
Non-interactive execution requires an explicit one-run acceptance or matching stored
consent. Strict offline mode rejects cloud endpoints. Credentials are read only from
provider-specific environment variables or a future secure store and are never persisted.

The deterministic mock provider is in-process test infrastructure, performs no API call,
and requires no privacy consent.

## 7. Failure, retry, resume, and batches

Each editable chunk has an immutable operation identity derived from selected-source,
prompt, correction configuration, and chunk hashes. Completed validated responses may be
resumed only when all identity inputs still match.

Retries are bounded and apply only to explicitly retryable transport/rate-limit/server
failures. Invalid provider content is permanent for that attempt and is never silently
accepted. A partial job publishes no transcript revision. Directory processing is
deterministically ordered, non-recursive by default, and isolates job failures according
to the existing batch continuation setting.

## 8. Provenance and artifacts

Published revisions use `provenance.method = "llm"` and record provider, model,
`local|cloud`, prompt ID/hash, and non-secret effective parameters. Detailed audits add
the provider-proposed change list and the independently reconstructed local change list;
the latter remains authoritative. Secrets and full request payloads are excluded.

## 9. Benchmark contract

Private benchmark data stays outside Git. A non-secret manifest selects inputs and gold
by exact hashes and revision lineage. Supported comparisons are:

- canonical result to latest accepted gold;
- earlier compatible revision to latest accepted gold.

The repository contains only synthetic fixtures and generic tooling. Reports include the
metrics required by FR-K18 and enough non-secret configuration/provenance to reproduce a
run. Provider benchmarks are reported separately; a cloud score must not be presented as
a local-provider score or vice versa.
